# GPIO 健壮写法速查：什么时候会「看起来对、实际错」

> 用途：接线正确、代码能跑之后，查**什么情况下会给出看似正常实则错误的结果**，以及怎么用只读手段复核。按症状定位，不要通读。
> 边界：引脚号、电气限值、三套编号、控制路径选型见 [`rpi-gpio-pinout.md`](./rpi-gpio-pinout.md)；板上配置归 [`rpi-network.md`](../access/rpi-network.md)，电脑侧归 [`rpi-ssh.md`](../access/rpi-ssh.md)，SoC 规格与欠压归 [`rpi-3b-hardware.md`](../hardware/rpi-3b-hardware.md)。证据分档与敏感规则见 [`docs/README.md`](../../README.md)。
>
> 主体依据是官方 GPIO 文档、内核 GPIO 接口文档与 libgpiod 上游提交；**第八节有本板 `[板上实测]`（2026-10-19），其余各节是手册层**。本章**没有任何一条带负载或涉及写操作的实测**。

## 二、异常退出后引脚回不到「上次电平」

| 项 | 结论 |
| --- | --- |
| 症状 | 段错误、`kill -9`、断电重启后继电器仍吸合 / 电机仍转；`finally` 没跑到就没人复位 |
| 内核语义 | 线的状态保证维持**直到 fd 被关闭**；fd 一关就「userspace 不可控，可能回默认态」（`GPIO_V2_GET_LINE_IOCTL`） |
| 所以默认态是什么 | 输入 + 默认 pull（「Power-on states」）；默认上拉的脚被约 50–65 kΩ 拉到 3.3 V |
| 流传说法的错处 | 「异常退出后保持上次状态」对 gpio-cdev 路径**是反的**；只有 mmap 直写寄存器才真的保持最后电平。`rpi-gpio-pinout.md`「十二、常见坑清单」第 3 条已按此改写，两篇同口径 |
| 真正危险 | 不是高或低，而是**高阻输入**：输出级断开，电平由弱上拉与漏电流决定，随时间漂移 |
| 防线 1（唯一兜底） | **硬件默认关断**：继电器/电机/舵机用外部 MOS 或驱动板，把「断电即关」做进电阻网络；固件只负责开机后主动打开 |
| 防线 2 | `finally` / `gpio_free` / `gpiod_line_release` 照写，但当成锦上添花，不是安全边界 |
| 防线 3 | 需要上电即位的安全锁、报警器：默认态必须是「关」，靠负载设计而不是靠固件开机去设 |

## 三、上电与重启瞬间的电平

| 项 | 结论 |
| --- | --- |
| 症状 | 按下电源，用户程序还没起来负载就动作了一下；每次重启都出现 |
| 成因 | 复位后全部 GPIO 回通用输入并施加默认 pull，直到用户态 `claim`；窗口长度＝固件启动＋服务拉起，systemd 管理下可达数秒 |
| 固定上拉的脚 | **GPIO2 / GPIO3 上拉不可软件关闭**（官方「Inputs」），其余可配——拿 I²C 两脚当通用输出时要记住 |
| 防线 | 与第二节同源：用外部硬件把「默认输入态」映射成「负载关断态」（上拉常态配 active-low 负载），这是唯一覆盖固件窗口的办法 |
| 口径 | 别把安全寄托在服务启动顺序上；`rpi-gpio-pinout.md`「十一、接线守则速查」已有结论一行，本章只给成因 |

## 四、设备与句柄占用

| 项 | 结论 |
| --- | --- |
| 症状 | 报 `EBUSY` 起不来；或两个进程都以为自己在控同一脚，输出打架、间歇性无规律出错 |
| 内核语义 | 独占：`GPIO_V2_GET_LINE_IOCTL`  granted exclusive access；**请求已占用的线是错误（EBUSY）** |
| 边界（必须记住） | 独占只覆盖 gpio-cdev 路径（libgpiod / lgpio / gpiozero / `gpioset` / `gpioget`）。**直接 mmap `/dev/gpiomem` 完全绕过仲裁**——不占线、不申请、不检查，天然能打架 |
| 与窗口数无关 | 「第二个进程」不必是另一个 agent：没退干净的自己、一个 systemd 服务、别的终端里的脚本都会造成占用。本仓单窗口推进不改变这条风险 |

| 排查动作（按副作用从低到高） | 命令 | 看什么 |
| --- | --- | --- |
| 1 | `gpioinfo -c gpiochip0` | 每条线被谁持有（consumer 名＝claim 时传的字符串）；**不要先跑 `gpioset`** |
| 2 | `sudo fuser -v /dev/gpiochip0` | 哪些进程开着这个 chip |
| 3 | `sudo lsof /dev/gpiochip0` | 同上，换工具交叉验证 |
| 4 | `ps aux \| grep …` | 前三步都不确定才猜进程 |

| 防线 | 做法 |
| --- | --- |
| consumer 名写清楚 | `gpiod_line_request_output(line, "little-sum-relay", 0)` 的第二参数会出现在 `gpioinfo`；写 `"test"` 或留空等于放弃线索 |
| 引脚分配显式约定 | 谁用哪几脚写在案子里，与串口/调试端口占用约定同级，不靠「我先开一下试试」 |
| 禁止项 | 他人可能在用的窗口里**不跑 mmap、不裸跑 `gpioset`**；`EBUSY` 是安全的失败模式，失败得响比静默共写好 |
| 读到 `EBUSY` 时 | 先怀疑「有人在跑」，而不是「代码写错了」 |

## 五、去抖与边沿检测

| 机制 | 口径 | 结论 |
| --- | --- | --- |
| 硬件同步窗口 | 官方「Interrupts」：常规边沿检测要求**三周期窗口内稳定**（记录成 `100` 或 `011`）才算一次跳变 | 机械触点抖动远宽于三个 CPU 周期，**这一层几乎挡不住按钮抖动**，别当去抖用 |
| 异步检测 | 绕过同步，能捕极窄脉冲 | **同样不去抖** |
| 软件去抖时长 | 官方 GPIO 文档未给；gpiozero 默认值本轮未查上游 | **任何具体毫秒数现在都不能写进文档**（见第九节第 3 条） |
| 轮询 vs 中断误差量级 | 无官方口径，且用户态叠加调度抖动 | **不要引用任何「亚毫秒」之类数字** |

| 防线 | 做法 |
| --- | --- |
| 按钮 | 一律软件去抖，时长按实测标定；实现为状态机「跳变后进忽略窗口，窗口内全丢」 |
| 正交编码器 | **必须四倍频解码**（A 相为准、B 相判方向，解码写在回调里）；只听 A 相单边沿必然丢数，与快慢无关 |
| 回调 | 只做最小工作（计数、置 flag、塞队列），处理放主循环；回调里耗时＝挤压其它中断，表现就是丢事件 |
| 窄脉冲 | 才用异步检测，并明确它不解决抖动 |
| 怀疑丢事件 | 先量事件率再动代码——间歇性问题多数不是去抖不足，是回调太慢 |

## 六、libgpiod 1.x 与 2.x 在错误处理上的差异

| 项 | 1.x | 2.x | 会怎么咬人 |
| --- | --- | --- | --- |
| 总体约定 | 失败设 `errno`；`int` 返回 -1、指针返回 NULL（v2.0 迁移提交明写沿用） | 同 | — |
| `chip_open` 失败 | 返回 `int` 句柄，失败是**负的 errno**：`if (ret < 0) strerror(-ret)` | 返回对象指针，失败是 `NULL`：`perror()` / `strerror(errno)` | **两套不能互抄**，抄错打印出莫名其妙的信息 |
| 生命周期 | 引用计数 `gpiod_chip_ref()` / `unref()`，多线程共享句柄安全 | **引用计数整体移除**，显式 `gpiod_chip_close()` | 1.x 的直觉到 2.x 就是 use-after-free / double-free 温床；长驻多线程升级时逐处复查 |
| 配置错误时机 | 配置函数返回值，可当场检查 | 「attributes」概念移除，配置函数**不返回值**，错误推迟到 request | 检查点必须移到 request；配置阶段做的检查是无效检查 |
| 配置过复杂 | 不会出现 | request 时 `errno = E2BIG` | 照抄旧教程会漏掉这个分支 |
| 方向与边沿选项 | `request_type` 里一起给 | 拆出（`gpiod_line_request_flags_rise/fall/edges()`） | 函数名对照表见 `rpi-gpio-pinout.md` 第十节 |

| 防线 | 做法 |
| --- | --- |
| 动手前先认版本 | `pkg-config --modversion libgpiod` 或 `dpkg -l 'libgpiod*'`；本板 **2.2.1** |
| 错误集中处 | 全部失败判断贴着 **request 调用**写 |
| 2.x 错误 | 一律走 `errno`，不去解释返回值里的负数 |
| 多线程 | 每线程独立 chip 对象，或主线程独占模型；别沿用 ref/unref 直觉 |

## 七、长驻程序的失效模式

共同特征是**没有明确故障时刻**，所以很难靠日志定位；根因几乎都是「配置期该做的事被放进了运行期」。

| 失效模式 | 成因 | 防线 |
| --- | --- | --- |
| fd 泄漏 | 循环里反复 `gpiochip_open`，`close` 只走 `finally` | **claim 一次用到底**；进程内 chip 做成单例 |
| 反复 claim / free | 每次都是内核往返，且释放瞬间引脚回默认态 | claim 频率降到「配置期一次」 |
| PWM 频率漂移 | 软件 PWM 由 CPU 忙等产生，负载一高就被抢占 | 精度敏感一律用硬件 PWM（集合见 `rpi-gpio-pinout.md`「八、Python 控制」） |
| 日志写满 SD | 无轮转的高频日志 | `logrotate`，或高频日志写 `/dev/null` 只留告警 |
| 异常后不释放 | 只写了正常路径清理 | 所有退出路径统一 `try/finally`，或 `atexit` / 信号处理 |
| 多线程共享句柄 | 见第六节，refcount 已移除 | 每线程独立对象 |

`nanosleep` / `time.sleep` 精度随负载漂移的量级**手册未述**，见第九节第 6 条，不写数字。

## 八、复核手段：确认「程序以为的」与「内核实际的」一致

成因几乎总是**认知偏差**而非程序 bug：认为线是自己持有的、认为编号是 BCM 号、认为自己设了方向——三条里任一条与内核实际不符，日志就会自洽地错下去。下列命令**全部只读**，别人在用板子时也能安全执行。

| 命令 | 本板 `[板上实测]` 2026-10-19（libgpiod 2.2.1）读数 | 判读 |
| --- | --- | --- |
| `gpiodetect` | `gpiochip0 [pinctrl-bcm2835] (54 lines)`、`gpiochip1 [brcmvirt-gpio] (2)`、`gpiochip2 [raspberrypi-exp-gpio] (8)` | 主控制器是 chip0，BCM0–53；另有 `/dev/gpiochip4` 符号链接 |
| `gpioinfo -c gpiochip0` | `line 0: "ID_SDA" input` | 逐线方向、值与 consumer 名 |
| `gpioget -c gpiochip0 17` | `"17"=inactive` | **2.x 的读数形态不是裸电平**；`[[ "$(gpioget …)" == 0 ]]` 这类旧脚本会静默走 else 分支，比跑不通更阴 |
| `pinctrl get 17` | `17: ip    -- \| lo` | 空闲脚默认态在本板的样子：输入、无偏置、电平 lo |
| `pinctrl funcs 17` | `GPIO17, FL1, SD9, DPI_D13, RTS0, SPI1_CE1_N, RTS1` | 该脚复用集合 |
| `pinctrl -v` | 自报 `bcm2835 (54 gpios)` | 与 `gpiodetect` 的 54 线互证；`pinctrl` 与 libgpiod **两套视角同时可用、互不干扰** |
| 提权需求 | 这批都在 `/usr/bin`，非交互 SSH 直接可敲 | GPIO 只读复核**不需要 sudo**；`sudo` 只在写线和看别人占用时用 |
| 写错的形态 | `gpioget 0 17` → 两行 `cannot find line '0'` / `'17'`，退出码 **1** | 2.x 的位置参数是**线**不是 chip，chip 必须 `-c`；这条可直接当脚本判别用（完整版本对照见 `rpi-gpio-pinout.md` 第九节） |

| 日志与现实不符时怎么判 | 依据 |
| --- | --- |
| 方向对、值对，但 consumer 名不是你 | 你读的是别人的引脚 → 第四节 |
| 值那一列是 `ACTIVE LOW` / `ACTIVE HIGH` 而不是你以为的 | 程序没持有这条线，它处于默认输入态或被别进程设成事件输入 |
| 程序说写成功、`gpioget` 读回相反 | 先怀疑编号搞错（物理针号当 BCM 号），而不是怀疑内核 → `rpi-gpio-pinout.md`「四、三套编号并存」 |
| `gpioinfo` 显示某线有消费者而你从没碰过 | 某个服务、某个 HAT 或另开着的调试进程在用 |
| 两套视角状态不一致 | 以 `gpioinfo` 为准（它反映内核实际占用关系） |
| 排查阶段 | **不要用 `gpioset` 做排查**，它是写操作，会改别人正在用的引脚 |

## 九、存疑清单：手册未述，需上板

以下全部没有权威手册依据，不写成事实；验完再回填。

| # | 存疑项 | 为什么裁不了 | 上板怎么验 |
| --- | --- | --- | --- |
| 1 | 复位后实际落到哪个 pull 状态 | 官方文档指向 Arm peripherals datasheet 的 AF 表，本轮未取得 | 万用表量静态电平 ＋ `pinctrl get` 对照 |
| 2 | 一次 `claim` 是否必然产生电平翻转、宽度多少 | 官方只写「接管前是输入态」，没写接管时序 | 示波器/逻辑分析仪打一次 claim |
| 3 | gpiozero 默认去抖时长 | 本轮未查其上游文档 | 读源码默认值 / 查其文档 |
| 4 | 轮询 vs 中断的误差量级 | 无官方口径 | 已知频率信号源对拍 |
| 5 | lgpio 与 RPi.GPIO 同时 claim 同一线是否必然 `EBUSY` | `EBUSY` 是内核语义，两库上层封装未验 | 起两进程抢同一线看返回 |
| 6 | `sleep` 精度随负载漂移的量级 | 手册未述 | 负载下测长周期 sleep 误差 |
| 7 | fd 泄漏累积速度、日志写满 SD 的时间 | 与介质和日志量强相关 | 长期跑 ＋ `ls /proc/<pid>/fd \| wc -l` |
| 8 | `lgpio.tx_pwm` 走的是硬件 PWM 还是软件定时 | lgpio 上游文档本轮取不到（抓取失败、仓库内路径 404），另有名字带 `hardware_` 的 PWM 函数，关系未权威核对 | 上板用示波器量同一个调用在硬件 PWM 脚（12/13/18/19）与其他脚的波形是否不同 |

**这八条不解决，本章对应段落给的是按手册口径的保守做法，不是实测最优解。**
